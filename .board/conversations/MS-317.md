## 3. Tech stack

**Frontend — two shells, both no-build, both vendored (no bundler, no npm runtime deps in the browser):**
- **Desktop web**: plain multi-page HTML + **Alpine.js 3** + Tailwind (compiled to `public/mosaic.css` via `npm run build:css`). ~35 pages in `public/*.html`; "routes" are literally filenames (`calendar.html`, `service-guide.html`, `peoples-page.html`, …).
- **Mobile shell**: **Preact + htm** (no JSX, no build step) at `public/mobile.html` + `public/mobile/*.js` (`app.js`, `destinations.js`, `screens-*.js`). Routing is in `public/mobile/destinations.js`.
- `public/index.html` picks the shell at runtime: native Capacitor → mobile; browser at phone width with touch → mobile; else desktop. `?shell=web` / `?shell=mobile` overrides, remembered in `localStorage`.
- All third-party libs are vendored into `public/vendor/` (Alpine, Preact, htm, Firebase compat SDK, jsPDF, Quill, TipTap, Fuse, Sortable, Lucide, Mammoth) by `scripts/vendor-assets.mjs` / `scripts/asset-manifest.mjs`. Nothing loads from a CDN.

**Native**: **Capacitor 8** (`capacitor.config.json`, appId `com.mosaicmanagercstx.app`, `webDir: public`), with `android/` and `ios/` projects. No Electron. No custom Capacitor plugins — `android/app/build.gradle` pulls only `capacitor-android` and `capacitor-cordova-android-plugins`. (Relevant to you: a native print/Bluetooth plugin would be the first one added.)

**Backend**: **Firebase** end to end.
- Cloud Functions v2, Node 20, in `functions/` (`index.js` plus ~25 modules). Deployed as its own bundle; shared pure domain modules are copied from `public/` into `functions/shared/` by `scripts/sync-shared-to-functions.js` (a `predeploy` hook).
- Firestore (`firestore.rules`, `firestore.indexes.json`), Firebase Auth, Firebase Storage.
- **Hosting, two sites** (`firebase.json`): `mosaic-hymn-database` serving `public/`, and `mosaic-hymn-mcp` serving `mcp-site/` with rewrites to the `mcp` function (ADR-0038). Note the hosting `Cache-Control` comments in `firebase.json` — HTML/JS/CSS are `no-cache`, `vendor/**` and fonts are `max-age=604800`, and the ordering of those blocks is deliberate.
- Local dev: `firebase emulators:start` (hosting on :5005, functions :5001, firestore :8080, auth :9099). Tests: `npm test` → `node --test`; emulator tests via `npm run test:emulator`.

# Chrome → Zebra ZD421 label printing via `window.print()`: research findings

**Short answer up front:** Yes, technically doable, but "acceptable quality and no dialog" both have real gotchas. `@page { size: 2in 3in }` is old, well-supported CSS, but Chrome has a *long-standing, still-open* bug where the print-preview/print-dialog paper-size picker doesn't reliably follow it — so getting the *physical* label size to actually go to the printer needs either `--kiosk-printing` + a pinned default paper size policy, or you're gambling on whatever paper was last selected. The page also gets zero feedback if the label printer is out of stock or the lid is open — `window.print()` returns `undefined` and there's no error channel. And Zebra's own web-printing guide (2016, still the current one) doesn't even list "browser → Windows driver → HTML" as one of its supported methods; it recommends SDK/socket-based ZPL printing instead.

---

## 1. CSS `@page size` — syntax, support, and the paper-size mismatch bug

**Spec syntax** (CSS Paged Media Module Level 3): `size: <length>{1,2} | auto | [ <page-size> || [ portrait | landscape ] ]`. Two lengths = width then height of the page box. One length = a square. https://www.w3.org/TR/css-page-3/

So `@page { size: 2in 3in; margin: 0; }` is exactly the spec-defined way to say "2 inches wide, 3 inches tall, no margin."

**Chrome support:** old — caniuse (backed by MDN browser-compat-data) lists the `@page size` descriptor as supported from **Chrome 15**. https://caniuse.com/mdn-css_at-rules_page_size

**The catch — page box vs. printer paper size:** Chrome parses and lays out the page box correctly, but there is a long-running Chromium request, **"Respect CSS @page property when selecting paper size"**, asking Chrome to actually change the *paper size selected in the print dialog/print preview* to match the CSS. This exists both as the legacy Monorail bug id 238303 and its successor on the new tracker, issue 41010929 — both titles confirm the same open ask. I could not pull the full issue body (issuetracker.google.com requires a Google sign-in to render bug detail), but the bug's existence and title, and multiple independent write-ups, confirm the gap: Chrome will render your page at 2in×3in, but the print dialog's paper-size dropdown and the physical sheet Chrome asks the printer driver for can still default to something else (e.g., Letter/A4) unless the printer's own driver already exposes a matching stock size that Chrome auto-selects. https://bugs.chromium.org/p/chromium/issues/detail?id=238303 · https://issues.chromium.org/issues/41010929

Practical implication for a Zebra label: this is exactly why kiosk deployments pin a paper size via policy (see §4) instead of trusting `@page size` alone to drive the printer's fed sheet size.

## 2. Margins / unprintable area / headless differences

- `margin: 0` on `@page` removes Chrome's own header/footer print margin — this is the CSS-level equivalent of the "Margins: None" option in the print dialog UI; MDN's paged-media guide documents `@page` as the mechanism for setting margins for print. https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Paged_media
- **Headless print-to-PDF is a separate code path with its own defaults**, not just "the same as choosing Print." The DevTools Protocol `Page.printToPDF` command defaults to **paperWidth 8.5in / paperHeight 11in and 1-inch margins on all sides**, regardless of what your page's `@page` rule says, unless you explicitly pass `paperWidth`/`paperHeight`/margins in the API call. https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-printToPDF — and this divergence between interactive "Print…" and `--headless --print-to-pdf` behavior (including margin handling) is documented as a real, confusing gap by developers debugging it. (Community source, flagged UNVERIFIED for exact wording, but consistent with the DevTools Protocol default values above.) https://andre.arko.net/2025/05/25/chrome-headless-print-to-pdf/
- For your case (interactive `window.print()`, not headless), this mostly matters as a warning: don't assume headless/CLI printing tests will reproduce dialog-based print behavior — margins and page-size defaults are handled differently in the two paths.

## 3. `@media print` — hiding everything but the label

Standard, well-documented MDN pattern: wrap non-label chrome in a print stylesheet or a `@media print` block and set `display: none`.

```css
@media print {
  #header, #footer, #nav { display: none !important; }
}
```
https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Media_queries/Printing

MDN also notes `@page` (size, margins, orientation) is the complementary at-rule for controlling the printed page itself, and that you can link a dedicated print stylesheet via `<link media="print">`. Same page above.

## 4. Kiosk printing flag + enterprise policies

**`--kiosk-printing`** — I found the actual Chromium source definition, not just secondary write-ups:

- Switch string: `"kiosk-printing"`
- C++ constant: `kKioskModePrinting`
- Chromium's own comment on it: **"Enable automatically pressing the print button in print preview."**
https://chromium.googlesource.com/chromium/src/+/HEAD/chrome/common/chrome_switches.cc

So mechanically: it doesn't remove the print pipeline, it auto-clicks "Print" inside print preview, sending the job to whatever printer print-preview currently has selected (last-used printer, unless you also force the OS-default via policy — see below). It does **not** require `--kiosk` — multiple independent reports describe it working standalone on desktop Chrome, only requiring `--kiosk` on ChromeOS/Edge kiosk-managed devices. This is corroborated by several community sources, not a primary spec doc, so treat the "standalone works fine" claim as UNVERIFIED at spec-grade even though it matches the source comment's behavior. https://gist.github.com/sajinct/cf4863f7b5da061b2c65c104c55a6da6

**Known reliability wrinkle:** Chromium bug 169004 / issue 40959316, "`--kiosk-printing` switch still shows a flash of the Print dialog for ~1 sec," documents that the dialog isn't fully suppressed — it flashes on screen briefly before auto-submitting, and search-result summaries describe this as long unowned/unresolved. Full bug text again required Google sign-in so I'm relying on secondary confirmation of the title/nature, not verified first-hand body text. https://bugs.chromium.org/p/chromium/issues/detail?id=169004 · https://issues.chromium.org/issues/40959316

**Enterprise policies** (fetched via the Chromium-shared policy schema mirrored on Microsoft's Edge policy docs, since chromeenterprise.google itself is JS-rendered and returned only nav shell to automated fetch — noted as a fetch limitation, not a claim about content difference; Edge and Chrome share the same underlying Chromium policy definitions for these):

- **`PrintPreviewUseSystemDefaultPrinter`** (boolean) — "If you enable this policy, Print Preview uses the OS system default printer as the default destination choice. If you disable this policy or don't configure it, Print Preview uses the most recently used printer." https://chromeenterprise.google/policies/print-preview-use-system-default-printer/ (content verified via the Chromium-shared Edge policy doc: https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/printpreviewusesystemdefaultprinter)

- **`DefaultPrinterSelection`** (string, JSON) — schema `{ idPattern, namePattern }` as regexes matched against printer id/name; first match wins; unset/no-match falls back to the built-in PDF printer or none. Example: `{ "idPattern": ".*public", "namePattern": ".*Color" }`. This is exactly the mechanism to pin a specific named Zebra queue as default. https://chromeenterprise.google/intl/en_ca/policies/default-printer-selection/ (verified: https://learn.microsoft.com/en-us/deployedge/microsoft-edge-browser-policies/defaultprinterselection)

- **`PrintingPaperSizeDefault`** (dictionary) — `name` is a standard size keyword or `"custom"`, and if custom, `custom_size: { height, width }` **in micrometers**. Example: `{"custom_size": {"height": 297000, "width": 210000}, "name": "custom"}` (that example is A4; for a 2in×3in label you'd compute micrometers: 2in = 50800 µm, 3in = 76200 µm). Important caveat baked into the policy itself: **"If the page size is unavailable on the printer chosen by the user, this policy is ignored."** — i.e., the Windows driver for the ZD421 has to actually expose/accept that custom size for this to take effect. https://chromeenterprise.google/intl/en_ca/policies/printing-paper-size-default/ (verified: https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/printingpapersizedefault)

- **`PrinterTypeDenyList`** — I was unable to fetch its live text (same JS-render limitation) and didn't independently re-verify its schema; I'd flag any specific claim about it as unverified rather than guess. Recommend re-checking directly at https://chromeenterprise.google/policies/?policy=PrinterTypeDenyList before relying on it.

**Bottom line for kiosk printing to a named Zebra:** yes — an admin can combine `DefaultPrinterSelection` (pin the ZD421 by name/id pattern) + `PrintingPaperSizeDefault` (pin the label's custom micrometer size, provided the Windows driver exposes that stock) + `--kiosk-printing` (auto-submit print preview) to get silent printing to the right printer at roughly the right size — with the flash-of-dialog caveat above, and contingent on the driver actually accepting that custom paper size (§1's bug and this policy's own caveat both point at the same weak link).

## 5. What the page learns when printing fails

- **`window.print()` returns `undefined`.** No promise, no callback, no status. It's also **synchronous/blocking**: JS execution pauses while the print dialog (or, under `--kiosk-printing`, print preview) is open. It throws nothing on failure. https://developer.mozilla.org/en-US/docs/Web/API/Window/print
- **`beforeprint`/`afterprint`** are pure lifecycle hooks — "about to print" and "print finished or dialog closed" — generic `Event` objects with no payload about outcome, printer state, or errors. MDN's own guidance is to prefer `@media print` over these events where possible; they exist for content swapping, not status reporting. https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeprint_event
- **Bluntly:** if the ZD421 is off, out of labels, or has its lid open, the web page learns nothing. The OS/driver may surface a Windows print-queue error, but nothing propagates back into JavaScript. `afterprint` fires regardless of whether the physical label actually came out. There is no standard web API for print-job/device-status feedback in this flow.

## 6. Zebra's own position

Zebra's **Web Printing Solutions** guide (P/N unrestricted, last revised September 2016 per its own document-control table — this is still the document currently hosted at the canonical URL) enumerates six supported architectures for web-to-Zebra printing: **TCP/IP Back-End, Cloud Connect, Browser Print, Enterprise Browser, RhoMobile, URL Schema.** https://www.zebra.com/content/dam/support-dam/en/documentation/unrestricted/guide/software/web-printing-solutions.pdf

Notably: **`window.print()` through the Windows print driver is not one of the six.** Every option Zebra documents routes print jobs as data (ZPL/CPCL over TCP sockets, WebLink/websocket, or the Browser Print local client app talking to Link-OS SDK) rather than through the OS print pipeline. This is a real gap in Zebra's own documentation for the driver+`window.print()` approach you're evaluating — Zebra doesn't warn about it because Zebra doesn't officially cover it in this guide at all.

On driver/rasterization behavior specifically, I could not find a primary Zebra document (driver install pages, ZD421 support page) that explicitly states "the Windows driver rasterizes HTML output to a bitmap." What the primary sources do confirm:
- The ZD421 support/driver page lists **"Windows Printer Driver v10"** and **"v8"** downloads and **Zebra Setup Utilities**, with no mention of browser/HTML printing guidance. https://www.zebra.com/us/en/support-downloads/printers/desktop/zd421.html
- Zebra's driver-install docs for the ZD421/ZD621 cover installation mechanics only (power sequencing, ZSU wizard), not rendering pipeline internals. https://docs.zebra.com/us/en/printers/desktop/zd421-and-zd621-desktop-printers-user-guide/setup-for-windows/installing-the-windows-printer-drivers.html
- General mechanism (not Zebra-sourced, standard Windows printing architecture knowledge, UNVERIFIED against a Zebra primary source): a GDI-class Windows printer driver for a thermal head necessarily receives a rasterized bitmap from the Windows print spooler for anything that isn't downloaded/native fonts or barcodes — the printer itself is a 1-bit-per-dot device at 203 dpi, so any anti-aliased web-rendered text gets dithered to black/white dots by the driver, which is a lossier path than native ZPL text/barcode commands sent directly. I did not find a Zebra-authored document stating this outright for the ZD421/driver-vs-ZPL comparison, so I'm flagging this whole paragraph as **UNVERIFIED against a Zebra primary source** — it's inferred from how GDI thermal drivers work generally, not confirmed in Zebra's docs.

# Research findings

## Topic 1 — Raw ZPL over TCP port 9100

**What port 9100 is on Zebra printers.** Zebra's own docs confirm port 9100 is the default "TCP raw" port wired straight to the printer's internal ZPL print engine — you open a socket and stream ZPL bytes, no protocol handshake. Zebra explicitly separates it from the JSON/SGD status port (9200) and documents the port-selection command (`ip.port`).
- [Default IP Ports Used by Zebra Link-OS Printers](https://support.zebra.com/article/000031643) (support.zebra.com)
- [ip.port SGD command reference](https://docs.zebra.com/us/en/printers/software/zpl-pg/r-sgd-wireless-sgd-wireless-commands/r-sgd-wireless-ip-port.html) (docs.zebra.com)
- [Concurrent TCP and Weblink connections to printer](https://developer.zebra.com/content/concurrent-tcp-and-weblink-connections-printer) (developer.zebra.com)

**Is it authenticated?** Zebra's port-list article itself doesn't use the word "authentication" — it just documents the port as a raw socket. But Zebra sells a separate add-on product, PrintSecure, whose own marketing copy is explicit that its job is to give you "tools to easily configure your printers to use secure connections... block unauthorized access" — i.e., that protection is not there by default. [PrintSecure product page](https://www.zebra.com/ap/en/products/software/barcode-printers/link-os/printsecure.html) (zebra.com). The broader claim that port 9100/AppSocket has no authentication or encryption layer by protocol design is well established security literature, but that specific characterization is not Zebra's own wording — flag it **UNVERIFIED against a primary Zebra source**, though it is consistent with Zebra's own PrintSecure positioning.

**Can Cloud Functions v2 reach it?** Yes for the "open an arbitrary TCP socket" part, no for "reach a device on a home LAN."
- Cloud Functions v2 / Cloud Run functions support **Direct VPC egress**, letting the function route outbound traffic (all-traffic or private-ranges-only) into a VPC network. [Configure Direct VPC egress for 2nd gen functions](https://docs.cloud.google.com/functions/docs/running/direct-vpc) (Google Cloud docs)
- Serverless VPC Access / Direct VPC egress only gets you into **Google's own VPC and whatever is peered to it** — Cloud Interconnect, Cloud VPN, or VPC Network Peering. There is no path from a Cloud Function straight to an arbitrary device on someone's home or church-office router. [Send serverless traffic to a VPC network](https://docs.cloud.google.com/vpc/docs/serverless-vpc-access) (Google Cloud docs)

**Bottom line, stated plainly:** reaching a printer sitting behind a home-grade router/NAT from Google Cloud is not realistic without first building a tunnel (Cloud VPN, a self-hosted VPN, or something like Cloudflare Tunnel/ngrok) terminating on-site. A church's internet connection almost certainly has a dynamic IP and no port forwarding configured, and even if it did, deliberately exposing an unauthenticated raw print socket to the public internet is a real security problem (this last point is general security reasoning, not a Google/Zebra doc claim, but it follows directly from the two confirmed facts above: no ingress path exists without a tunnel, and the port has no auth).

## Topic 2 — WebUSB / Web Serial on Windows against a Zebra printer with the Windows driver installed

**WebUSB basics.** `navigator.usb.requestDevice()` requires a secure context and (per MDN) transient user activation — it must be called from a user gesture such as a click. [USB: requestDevice() — MDN](https://developer.mozilla.org/en-US/docs/Web/API/USB/requestDevice)

**The Windows driver-claiming problem — confirmed at the source.** Chrome's own "Building a device for WebUSB" doc states plainly: on Windows, unlike other platforms, a USB device can't be opened by a web page unless the special **WinUSB** driver is loaded for it — "the basic requirement is that a device should not already have a driver claiming the interface the page wants to control." [Building a device for WebUSB — developer.chrome.com](https://developer.chrome.com/docs/capabilities/build-for-webusb)

Microsoft's own WinUSB docs describe exactly what installing WinUSB entails: either the device auto-installs as a "WinUSB device," or you manually switch its driver via Device Manager, or you ship a custom INF (with a device interface GUID) that installs `Winusb.sys` **as the device's function driver** — i.e., it replaces whatever driver currently owns that interface. [WinUSB (Winusb.sys) Installation for Developers — learn.microsoft.com](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/winusb-installation)

Putting those together: to WebUSB into a Zebra printer on Windows, you would have to replace the Zebra printer driver on that USB interface with WinUSB (Chrome's own doc mentions Zadig as the typical dev tool for this) — which means normal Windows/spooler-based printing to that device stops working. Neither Chrome's nor Microsoft's docs frame this as reversible without redoing the driver swap.

**Does the ZD421 support WebUSB/WinUSB out of the box?** No indication it does. The Zebra ZD421/ZD621 USB interface page only talks about USB 2.0 plug-and-play and links out to "Installing the Windows Printer Drivers" — no mention of WebUSB, WinUSB, or a WebUSB platform descriptor anywhere in Zebra's docs I could find. [USB Interface — docs.zebra.com](https://docs.zebra.com/us/en/printers/desktop/zd421-and-zd621-desktop-printers-user-guide/c-zd620-420-setup/c-zt4x1-connect-the-printer-to-a-device/t-zd421-zd621-ug-connecting-your-printer-to-a-computer/r-zd620-420-usb-interface.html) — confirms your expectation that Zebra doesn't document WebUSB at all.

**Web Serial.** MDN describes Web Serial as reaching devices that expose a serial port — either an actual serial port, or a USB device that emulates one (USB CDC-ACM), or Bluetooth SPP. [Web Serial API — MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Serial_API) A ZD421 over its plain USB printer interface is not a CDC-ACM serial device — you'd need Zebra's optional serial port module and an actual serial cable, per Zebra's own serial-interface docs. [Serial Interface — docs.zebra.com](https://docs.zebra.com/us/en/printers/desktop/zd421-and-zd621-desktop-printers-user-guide/setup/connecting-your-printer-to-a-computer/serial-interface.html)

**Browser support.** MDN's own compatibility notes for both APIs confirm Chromium-only: WebUSB works in Chrome/Edge/Opera, not Firefox, not Safari. [USB — MDN](https://developer.mozilla.org/en-US/docs/Web/API/USB) Web Serial: Chrome 89+, Edge 89+, Opera 75+, Firefox only very recently (151+); Safari unannounced. [Web Serial API — MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Serial_API)

## Topic 3 — Raw ZPL to a driver-installed printer, via a small Windows helper

**The Win32 sequence.** Microsoft's archived KB article gives the exact call sequence and sample code: `OpenPrinter` → `StartDocPrinter` (with `DOC_INFO_1.pDatatype = "RAW"`) → `StartPagePrinter` → `WritePrinter` (loop) → `EndPagePrinter` → `EndDocPrinter` → `ClosePrinter`. [Send raw data to printers by using Win32 API](https://learn.microsoft.com/en-us/previous-versions/troubleshoot/windows/win32/win32-raw-data-to-printer) (learn.microsoft.com — archived but still the canonical reference). Individual function docs: [StartDocPrinter](https://learn.microsoft.com/en-us/windows/win32/printdocs/startdocprinter), [WritePrinter](https://learn.microsoft.com/en-us/windows/win32/printdocs/writeprinter).

**RAW datatype bypasses driver rendering — confirmed.** Microsoft's driver docs state plainly: "RAW data can be sent to a print monitor without further processing. The print processor just sends this data back to the spooler by calling WritePrinter" — i.e., RAW is not rendered/transformed, it passes through untouched. [RAW Data Type — learn.microsoft.com](https://learn.microsoft.com/en-us/windows-hardware/drivers/print/raw-data-type) So no, you do not need a driver "passthrough" setting for the raw-spooler API route — `StartDocPrinter`/`WritePrinter` with `pDatatype="RAW"` already skips rendering regardless of which driver is installed on the queue.

**.NET route.** No supported managed API sends truly raw bytes — `System.Drawing.Printing` is explicitly documented as unsupported in services/ASP.NET and, since .NET 6, Windows-only ([PrintDocument class docs](https://learn.microsoft.com/en-us/dotnet/api/system.drawing.printing.printdocument?view=windowsdesktop-9.0)); it also renders via GDI rather than emitting raw bytes. Microsoft's own guidance for raw printing from managed code is P/Invoke into `winspool.drv` using the sequence above — this is stated in the community/support threads rather than a polished "how-to" page, so treat the specific "P/Invoke is the standard answer" framing as **largely UNVERIFIED against an official current MS doc** (the strongest primary evidence is that the only Microsoft-documented raw-printing path at all is the Win32 API above; there is no first-party managed wrapper for it).

**Node.js / no native code route.** I could not find a Microsoft doc describing `copy /b file \\host\share` or `net use LPT1: \\host\share` as an endorsed programmatic printing method — the material that exists is Microsoft Q&A forum threads, not documentation pages, e.g. [Mapping LPT1 to a shared printer — Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/2425451/mapping-lpt1-to-a-shared-printer) and [Net Use Command and Printing to text files — Microsoft Q&A archive](https://learn.microsoft.com/en-us/archive/msdn-technet-forums/161f58a8-c0d8-4119-96ee-37995443a892). **Label this whole approach UNVERIFIED / forum-only** — it is a real, commonly-used trick (map the shared printer to `LPT1:` via `net use`, then `copy /b` a raw ZPL file to it, which Windows treats as raw bytes to the print share), but it is not documented by Microsoft as a supported method, only discussed on their answers forum.

# ZPL / Zebra ZD421 Research — Primary Sources Only

## TOPIC A — ZPL Basics for a Nametag Label

**Source used:** *Programming Guide for ZPL II, ZBI 2, Set-Get-Do, Mirror, WML*, part number P1099958-001, dated 1/31/18 — served from Zebra's own document host, https://cpws.zebra.com/cpws/docs/zpl/zpl-zbi2-pm-en.pdf (confirmed Zebra-owned server via response headers: `X-Served-By`/cert chain resolve to zebra.com infrastructure). Zebra's newer public URL for this same guide 404s as of today, so this Zebra-hosted mirror is the primary copy I could retrieve in full; page numbers below are the guide's own internal page numbers ("ZPL Commands NN").

### `^XA` … `^XZ` — label format wrapper
- `^XA` = **Start Format**, the opening bracket for a label (ZPL Commands p.339). Can be sent as raw ASCII STX (0x02).
- `^XZ` = **End Format** (p.344). When the printer receives `^XZ`, the label actually prints. Can be sent as raw ASCII ETX (0x03).
- Every label must start with `^XA` and end with `^XZ` to be valid.

### `^FO` — Field Origin
Format: `^FOx,y,z` (p.176-177). x/y = 0 to 32000 dots, position of the **upper-left corner** of the field, measured from the `^LH` label-home point. z = justification (0 left / 1 right / 2 auto — firmware V60.14.x+ only). Units are always **dots**, not inches or mm.

### Fonts — `^A`, `^A@`, `^CF`
- `^CF f,h,w` (p.131) — sets the **default** font/height/width (dots) for every subsequent alphanumeric field until changed. Default font A, default height 9, default width = last permanent value.
- `^A f,o,h,w` (p.42-43) — sets font for the *next* `^FD` only, one-shot. f = font letter/number (A-Z, 0-9), o = orientation (N/R/I/B), h/w = height/width in dots (scalable fonts: 10–32000; bitmap fonts: multiples of base size).
- `^A@ o,h,w,d:f.x` (p.44) — same idea but calls a font by its **file name** (e.g. `E:SWISS721.TTF`) instead of a single-letter designator.

### `^FD` / `^FS` — data and terminator
- `^FD a` (p.167) — the literal data string for the current field, up to 3072 bytes.
- `^FS` (p.179) — **Field Separator**, ends a field definition. Can be sent as ASCII SI (0x0F).

### `^FB` / `^FW`
- `^FB a,b,c,d,e` (p.163-164) — **Field Block**: wraps/word-wraps `^FD` text into a box. a = block width in dots, b = max lines, c = inter-line spacing, d = justification (L/C/R/J), e = hanging indent of wrapped lines. Auto-hyphenates.
- `^FW r,z` (p.183-184) — **Field Orientation**: sets the *default* rotation (N/R/I/B) and justification for fields that don't specify their own. Persists until changed or power-off.

### Barcodes — `^BC`, `^BQ`, `^BY`
- `^BY w,r,h` (p.126-127) — sets barcode **module width** (1-10 dots, default 2), **wide:narrow ratio** (2.0-3.0, 0.1 steps, fixed-ratio codes ignore this), and **height** (default 10 dots). Stays active until reissued.
- `^BC o,h,f,g,e,m` (p.76-78) — **Code 128**. o=orientation, h=height (dots), f=print interpretation (human-readable) line Y/N, g=that line above the code Y/N, e=UCC check digit Y/N, m=mode (N/U/A/D — "A" = automatic subset selection). Data comes from `^FD`, width-limited to the label.
- `^BQ a,b,c,d,e` (p.106-108) — **QR Code**. a=orientation, b=model (1 or 2, 2 recommended), c=magnification 1-10 (default scales with dpi: 2 @ 203dpi, 3 @ 300dpi), d=error correction (H/Q/M/L, default Q), e=mask 0-7. Data is passed through `^FD` using QR "switch" syntax (`^FDQA,text^FS` etc.).

**Which is better for a 4-character security code?** `^BC` (Code 128). It's a 1‑D linear symbology cheap laser/CCD scanners at a check-in desk read reliably, it's compact for a 4-character alphanumeric string, and — critically — `^BC`'s `f` parameter gives you an automatic **human-readable line under the bars** for free, so a volunteer can eyeball-match the code without a scanner. `^BQ` (QR) needs a camera-class imager, has no built-in human-readable text, and is overkill for 4 characters — it's meant for URLs/larger payloads.

### Label geometry & media commands
- `^LL y` (p.264-265) — **Label Length** in dots. Needed for continuous media. Formula given in the guide: inches × dots-per-inch = y (203.2 dots/in at 8 dots/mm).
- `^PW a` (p.304) — **Print Width** in dots.
- `^LH x,y` (p.263) — **Label Home**, the origin point all `^FO` coordinates are relative to. Must come before the first `^FS`.
- `^MN a,b` (p.277-278) — **Media Tracking**: N=continuous, Y/W=web (gap) sensing, M=black-mark sensing, A=auto-detect, V=continuous variable-length.
- `^MD a` (p.271-272) and `~SD ##` (p.307) — **Media Darkness**. `^MD` is a relative adjustment (-30 to 30) to the current darkness; `~SD` sets an absolute two-digit value (00-30); the guide states the `~SD` value is *added to* the `^MD` value.
- `^PR p,s,b` (p.301-302) — **Print Rate**: print speed / slew speed / backfeed speed, values 1-14 mapping to 25.4–304.8 mm/sec depending on model.
- `^PQ q,p,r,o,e` (p.299-300) — **Print Quantity**: q=total labels, p=pause-after-count, r=serial-number replicates, o=override pause (Y/N), e=cut-on-error-label.

### Status & error queries
- `~HS` (p.207-210) — **Host Status Return**. Sends three `<STX>…<ETX><CR><LF>` strings back. String 1 field `b` = paper-out flag, field `c` = pause flag. String 2 field `o` = head-up / ribbon-out flag (dual use), field `p` = thermal-transfer-mode flag. **Important caveat directly from the guide**: *"When a `~HS` command is sent the printer will not send a response to the host if the printer is in one of these conditions: MEDIA OUT, RIBBON OUT, HEAD OPEN, REWINDER FULL, HEAD OVER-TEMPERATURE."* — i.e. `~HS` can go silent exactly when you need it most.
- `~HQES` (p.201-204, Tables 14-15) — **Host Query, Error Status**. Response format:
  ```
  PRINTER STATUS
  ERRORS:   1 00000000 0000000B
  WARNINGS: 0 00000000 00000000
  ```
  Each response line is `<flag> <nibbles 16-9> <nibbles 8-1>`; the last hex digit(s) are bitmasks: **Media Out = 1, Ribbon Out = 2, Head Open = 4, Cutter Fault = 8** (all in nibble 1, additive — e.g. `B` = 8+2+1 = cutter fault + ribbon out + media out simultaneously). "Paused" is a *warning* flag, not in this error table, and only listed for the KR403 model — general pause state is read via `~HS` string 1's `c` flag instead. `~HQ` also supports `HA` (network hardware address), `JT` (printhead test), `MA`/`MI` (maintenance), `OD` (odometer), `PH` (printhead history), `PP`, `SN`, `UI`.
- `^HH` (p.198) — **Configuration Label Return**: echoes the full printer configuration back over the same port as readable text (what you'd get on a printed config label), triggered as `^XA^HH^XZ`.

### Save/calibrate
- `^JUS` — I could not find a *standalone* `^JUS` command page; in this guide it is documented as the `S` parameter of `^JU` (**Configuration Update**, p.249-250): `^JUa` where a = F(reload factory)/N(reload factory network)/R(recall last saved)/S(**save current settings**). `^XA^JUS^XZ` is the idiom used throughout the guide to persist changes (e.g. after `^CM`, `^JH`, Communications Mode changes) across power-off.
- `~JC` (p.226-227) — **Set Media Sensor Calibration**: forces a label-length measurement and re-adjusts media/ribbon sensor values. No parameters. Note: there is no separate `^JC` (caret) command in this guide — only `~JC` (tilde) exists.

### Connectivity per SKU
- **Standard on every ZD421**: USB 2.0 and USB Host — confirmed in the "Standard Features" block of the tech-specs PDF: *"Connectivity: USB 2.0, USB Host"*.
- **Ethernet is never standard** — it always appears under the spec sheet's separate "Connectivity Options" heading: *"Field-installable 10/100 Ethernet"*, and the User Guide repeats this for the ZD421 specifically: *"ZD421 Field installable connectivity modules: Internal Ethernet Print Server (LAN, RJ-45 connector)... Serial (RS-232 DB-9) Port"* (contrast with the ZD621, which does ship with Ethernet+Serial built in).
- Also field/factory-installable: RS-232 serial, and wireless — either "Wi-Fi (802.11ac...), Bluetooth Classic 4.1, and Bluetooth Low Energy (LE) 5.0" or a newer "Wi-Fi (802.11ax...), Bluetooth 5.3" radio option, per the User Guide's printer-options section.

### Direct thermal vs. thermal transfer vs. cartridge
Confirmed by the tech-specs PDF's own naming: **ZD421d** = direct thermal, **ZD421t** = thermal transfer (ribbon roll), **ZD421c** = ribbon-cartridge model (uses Zebra's snap-in cartridge, described as "the only thermal printer to offer a ribbon cartridge that takes just a few seconds to load", per Zebra's ZD400-series product page, https://www.zebra.com/us/en/products/printers/desktop/zd400-series/zd421.html).

### 203 dpi vs. 300 dpi
Both are real, purchasable resolutions (tech-specs PDF, "Optional Features: 300 dpi print resolution (12 dots per mm)" vs. standard 203 dpi/8 dots per mm). **`^FO` dot coordinates and font-height/width values do NOT auto-scale between resolutions** — the guide's own `^LH`/`^LL` documentation gives *different* dots-per-inch conversion factors per printhead density (152.4 dots/in @ 6 dots/mm, 203.2 @ 8 dots/mm, 304.8 @ 12 dots/mm, 609.6 @ 24 dots/mm — ZPL II Guide p.264-265). A label built in dots for 203 dpi will physically print ~1.5× smaller if sent unchanged to a 300 dpi head. I found **no `^JM` or other ZPL command in this guide that auto-rescales a format between resolutions**; the guide instead expects you to recompute coordinates using the dots-per-inch table above, or design in real-world units and multiply by the target dpi yourself. (I did not find a primary Zebra source describing `^JM` — that command name does not appear in this programming guide at all; treat any claim about a `^JM` dpi-switch command as **UNVERIFIED** until seen in an actual Zebra doc.)

### Max print width & media
Per the ZD421 tech-specs PDF and matching current docs.zebra.com specs page:
- Max print width: **104 mm (4.09 in.)** general figure in the 2021 spec sheet table; the live docs.zebra.com page gives per-model figures — **108 mm DT**, **112 mm TT**, **118 mm cartridge**.
- Max media roll OD: **127 mm (5.0 in.)**. Core ID standard **12.7 mm (0.5 in.) or 25.4 mm (1 in.)**; with adapter kit, 38.1/50.8/76.2 mm (1.5/2/3 in.).
