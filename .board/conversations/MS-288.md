The MS-288 change adds `descriptionOf` (mirroring the existing `locationOf`) to `events-occurrence-core.js` (and its `functions/shared` twin), a per-date "description" box on `calendar-event.html`, and extends `saveOccurrenceDetails` in `events-store.js` so a description-only edit on a bare date of a series creates that occurrence document.

**The visibility-stamping code (ADR-0018) is correct.** `events-store.js` (`saveOccurrenceDetails`, ~lines 950–990) stamps a newly-created occurrence with the series' `visibility`/`rosterShared` via `stampFor`, leaves an existing document's stamp alone, and writes `seriesId`/`date` so the two-query visibility read in ADR-0018 §5 still finds it. `test/events-store.test.js` (~1757–1791) covers exactly this, including the Sunday-Service-is-always-public case. No contradiction with the ADR.

**The real finding is a model/code conflict, not a bug.** CONTEXT.md states, as an explicit architectural line under **Event occurrence**:

> "**One date decides WHO; the Event decides WHAT.** ... Which Roles an Event carries, who may see it, and what colour it draws are true of every date, so they are set once in [[Event series management]]."
(`CONTEXT.md` ~line 549-552)

and under **Event series management**:

> "everything true of every date: its name, start time, place, **description**, recurrence pattern, [[Event visibility]], colour" (`CONTEXT.md` ~line 570-571)

MS-288 gives one date a description that can differ from, and override, the series' — a genuine per-date "WHAT," not a "WHO." The code is fully aware it's doing something new here and argues for it at length:

> "unlike a place it is expected to differ: 'bring the trestle tables, we're eating after' is true of one week and wrong for the rest." (`public/events-occurrence-core.js` ~line 443-445, mirrored in `functions/shared/events-occurrence-core.js`)

and the UI panel is titled accordingly:

> "Just this date ... Anything true of every one of these belongs on the event itself." (`public/calendar-event.html` ~line 598-603)

`calendar-event.js`'s `occurrenceOwnFields` getter (~1591-1595) enforces the same split in code: a series date owns only `['description']`; everything else (`name`, `date`, `endDate`, `time`, `location`) stays event-only, one-offs excepted. So the code carves out exactly one exception to "the Event decides WHAT," and CONTEXT.md's two passages above still state the rule without that exception. This is worth a human call: either CONTEXT.md's "everything true of every date" line needs a carve-out for description, or the feature needs to be reconsidered against a model that was deliberately drawn that way. I'm not picking a side — just flagging that the two currently disagree, in the exact section the ticket touches.

**The stale line is confirmed.** CONTEXT.md ~line 571 says Event series management is "Reached at `calendar-event.html?series=<id>`." But `public/calendar-event.js` (lines 48, 308, 392, 787) now redirects there to `recurring-events.html?series=<id>`, and `public/recurring-events.js` itself narrates the move in comments: "to be a second page at `calendar-event.html?series=…`" (line 12) and "so `calendar-event.html?series=` is not a page any [more]" (line 878, MS-229 cited explicitly). CONTEXT.md was not updated by MS-288 even though this diff edits `calendar-event.js`/`calendar-event.html` directly — the exact files whose own comments record that the URL in CONTEXT.md is dead. It would have cost nothing to fix while in there, but it's a pre-existing staleness, not something MS-288 introduced.
