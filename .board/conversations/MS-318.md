## MS-318 Research: Kiosk Attendance — What Exists vs. What's Net-New

### 1. Account / auth model

**Exists:**
- Users live in `users/{uid}` with a `permissionLevel` field (legacy fallback `role`), one of a flat enum: `viewer → member → editor → elder → admin → super_admin` (`public/auth.js`, `firestore.rules:9-65`).
- **Critical nuance, explicitly flagged in `CONTEXT.md:815` ("Flagged ambiguities")**: this is *not* a strict hierarchy. `isElder()` = `['elder','super_admin']` and `isAdmin()` = `['admin','super_admin']` are parallel branches — an `admin` cannot see elder/pastoral data. Any new "kiosk" tier needs to be designed the same way: an explicit `in [...]` allowlist, not an assumption that it slots below/above something on the line.
- **Route-gating is client-side, per-page, and repeated ~30 times** (`public/*.js` — `shepherding-dashboard.js:36-47` is a representative example): each page's `init()` does `auth.onAuthStateChanged` → `getUserData(uid)` → checks `['elder','super_admin'].includes(permissionLevel)` → `window.location.href = 'index.html'` if not. There is no shared router/guard module — it's copy-pasted per page.
- **The real enforcement is server-side**, in `firestore.rules` (`isSignedIn()`, `isMember()`, `isEditor()`, `isElder()`, `isAdmin()` helper functions, `firestore.rules:9-65`). The client-side redirect is UX only — CONTEXT.md is explicit about this pattern elsewhere ("The *page* is still member-and-above: this is the lock, not the door" — `CONTEXT.md:104`, ADR-0031).
- Account creation is locked to `permissionLevel == 'viewer'` on self-create (`firestore.rules:83-93`) — a kiosk account almost certainly can't be self-signed-up the same way; it'd need an admin-provisioned path.
- **Anonymous Firebase sessions are deliberately excluded** from `isSignedIn()` (`firestore.rules:14-36`) — relevant if a kiosk device was tempted to use anonymous auth for simplicity; the existing security model treats that as equivalent to signed-out.

**Net-new / open decisions:**
- No "kiosk" account type exists anywhere (zero hits repo-wide for "kiosk").
- Where it sits in the permission model is a real design question: full new enum value + new rule helper (`isKiosk()`) + updates to every one of the ~30 per-page client guards that use hardcoded permission arrays, or a different mechanism entirely (e.g., a shared device credential that isn't a `permissionLevel` at all, more like a scoped API key/custom claim). This alone is a non-trivial slice of the ticket.
- Provisioning/rotation of kiosk device credentials is undesigned.

### 2. Family / person directory model

**Exists — Family is a real first-class entity**, not implicit on Person (`CONTEXT.md:126-129`, ADR-0012):
- Own `families` collection: `{ husbandId?, wifeId?, childIds[], anniversary? }`. Husband/Wife are single Person refs; children is a shared list. Multi-generation trees are emergent (walk child → their-own-Family-as-spouse → children), not nested.
- Firestore rule: `families/{familyId}` — read `isSignedIn()`, write `isEditor()` (`firestore.rules:516-519`).
- Person document (`people/{personId}`) has `name`, `contact.{email,phone,address}`, `sex`, `membership.{status,joinedAt}`, etc. — **no family/household field on Person itself**; the relationship is entirely via the `families` collection referencing Person IDs.

**Search — client-side only, no index, no family search:**
- `public/peoples-page.js:220-223` loads the **entire** `people` collection into memory (`db.collection('people').get()`), then filters in JS.
- Search is `list.filter(p => p.name.toLowerCase().includes(term))` (`peoples-page.js:1094-1096`) — substring match on individual Person name only.
- **There is no family name/label field anywhere in the schema** (confirmed by grep — zero hits for `familyName`/`householdName` in app code) and no query path that searches "by family." To find a household today you find one person, then read their Projected Relationships (spouse/children) off the `families` collection.

**Flag for sizing:** "search by family" is genuinely net-new — there's no family-level searchable attribute (families aren't named), the only existing search is a full-collection client-side scan (fine for an internal directory list, likely wrong shape for a kiosk needing fast lookup), and building "type a name, see the household" would mean either (a) a client-side join over the already-loaded people+families (cheap, reuses what exists), or (b) an actual index/service if the kiosk needs scale/perf guarantees a full-collection load can't give. This is plausibly its own sub-task even if small.

### 3. Event model & "who served" pattern (attendance should mirror this)

**Exists — extensively documented in `CONTEXT.md:409-651` and ADR-0016/0018/0019/0020/0021:**
- **Event series** (`events` collection) — recurring definition (roles, recurrence rule, visibility).
- **Event occurrence** (`event_occurrences/{seriesId}_{date}`) — one dated instance, sparse (only exists once something is recorded against it), carries `participantIds` denormalized for visibility checks.
- **Assignment** — a Person placed in a Role slot on an occurrence: **the plan, mutable**. States: Pending → Confirmed / Declined. Lives in a `roster` **subcollection** on the occurrence (deliberately not a field — "Firestore cannot hide a field from a reader" — same reasoning that would apply to kiosk-visible-only fields, see Q4).
- **Involvement** — the actual "did serve" record: **the fact, immutable, never for a future date** (`CONTEXT.md:451-460`). Stored at `people/{personId}/involvement/{involvementId}`.
- **The conversion mechanic** (`functions/index.js:2254-2308`, `convertConfirmedAssignments`): a **scheduled Cloud Function running daily at 00:30 church-local** walks past `event_occurrences`, reads each `roster` subcollection, and for every **Confirmed** assignment writes an Involvement record; Declined never converts; Pending is left as an open question for an editor. It's idempotent (deterministic doc id from occurrence+role+slot+person).
- Rules: `people/{personId}/involvement/{involvementId}` — read `isSignedIn()`, write `isEditor()` (`firestore.rules:434-437`), plus a collection-group read rule for cross-person queries (`firestore.rules:483-488`).

**Important mismatch to flag for the ticket:** the "who served" pattern is fundamentally **retrospective/batch** — it converts a *plan* into a *fact* the day after the date passes, driven by a Confirmed Assignment (an RSVP made in advance). Kiosk attendance is presumably **real-time, same-day, walk-up** — there's no pre-existing "plan" to confirm; someone taps a name at the kiosk and that itself is the fact. So "attendance should follow the same pattern as who served" can mean *reuse the data shape* (a fact record on the Person, dated, role/type-tagged, written once) but the *write path* is necessarily different (immediate client/kiosk write vs. nightly scheduled conversion of a pre-existing plan). Worth pinning down explicitly in the PRD which half of the pattern is meant.

### 4. Security rules

**Location:** single `firestore.rules` file at repo root (~37.5K, well-organized with named boolean helper functions and heavy inline commentary explaining *why*, not just *what*).

**Granularity — confirmed precedent both ways:**
- **Field-level restriction on WRITE exists and is precedented**: `people/{personId}` self-service update rule restricts a Linked User to only touching `['contact','birthday','sex','photoUrl','photoPath','photoCrop','updatedAt']` via `request.resource.data.diff(resource.data).affectedKeys().hasOnly([...])` (`firestore.rules:422-429`), and similarly `users/{userId}` self-update is restricted to `['dashboardCardOrder']` (`firestore.rules:97-98`).
- **Field-level restriction on READ does not exist and structurally can't** — Firestore security rules can only allow/deny a whole document, never a subset of its fields. The codebase already hit this exact wall and worked around it by **splitting sensitive data into separate documents/subcollections**: the event roster is a subcollection specifically because "Firestore cannot hide a field from a reader" (`CONTEXT.md:553`, `firestore.rules` comments around participant visibility), and shepherding notes/prayer requests/away-dates are all pulled off the main Person document into elder-gated subcollections for the same reason, while contact info stays on the main `people/{personId}` doc.
- **Consequence for the ticket's stated goal** ("kiosk reads names + family membership, not contact/notes"): today `people/{personId}` bundles `name` **and** `contact.{email,phone,address}` in one document, readable by any `isSignedIn()` account (ADR-0031's "the directory asks for an account" floor). A kiosk account, if just added to `isSignedIn()`, would get contact info too — there's no way to carve that out with a rule alone. To actually restrict a kiosk to names+family only, you'd need either: a new projection collection/subcollection holding just the kiosk-safe fields (mirroring how `roster` and `shepherding_notes` were split out), or a Cloud Function callable that server-side filters the response instead of a direct Firestore read. This is a real architectural decision, not a small tweak — flag as its own design question.
- Role-based restriction (not just field-based) is everywhere and easy to extend: `isElder()`, `isEditor()`, `isAdmin()`, `isMember()` are composable per-collection/per-subcollection (e.g. `prayer_requests` is `isElder()` only while `involvement` on the same Person is `isSignedIn()`).

### 6. CONTEXT.md / ADR relevant terms

Quoted above inline, but the load-bearing ones for this ticket specifically:

- **Family** (`CONTEXT.md:126-129`): "A first-class entity (its own `families` collection)... **Editor-authored, not elder-only**... A serving rule can name a Family, and it reads the directory." — confirms Family is real and already a first-class concept a Role/rule can reference; a kiosk reading "family membership" would read this same collection.
- **Membership Directory** / ADR-0031 (`CONTEXT.md:102-105`): "It asks for an account, not for membership... Every directory collection — the Person record, Family, the tag vocabulary, Involvement and pastoral-prayer history — is readable by anybody signed in and by nobody else." This is the existing floor a kiosk account would either fit under or need to be carved narrower than.
- **Involvement** / ADR-0016, 0018, 0019 (`CONTEXT.md:451-460`, `538-651`): the full "who served" model to mirror, detailed in §3 above.
- **Permission Level ambiguity** (`CONTEXT.md:815`): explicit warning that the tier list is not a straight hierarchy — directly relevant to where "kiosk" gets inserted.
- No ADR or CONTEXT.md entry mentions kiosks, attendance, or check-in as a domain concept — this ticket would be introducing genuinely new vocabulary, which (per this repo's own conventions) should probably get its own ADR once the shape is decided.

### Sizing flags — likely sub-projects within this ticket

1. **Kiosk account type / auth path** — new permission tier or entirely separate credential mechanism; touches `firestore.rules` helpers and potentially ~30 client pages' hardcoded permission arrays (though a kiosk UI is presumably one new page, not touching existing ones — worth clarifying scope).
2. **Field-level read restriction for kiosk** — Firestore rules cannot filter fields within a document; needs a new projection collection or a callable Cloud Function. Real architecture decision, not a rules tweak.
3. **Family/person search for the kiosk UI** — no family-level searchable field exists today; decide whether client-side scan (reuse existing pattern) is acceptable or a proper index is needed.
4. **Attendance write path** — decide whether it mirrors Involvement's *data shape* only, or also its *batch/retrospective write mechanic* (which doesn't fit a same-day kiosk check-in) — this is a modeling decision, not just implementation, and probably deserves its own ADR before coding starts.
